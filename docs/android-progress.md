## Goal (from the owner's request)

A native, offline-first Android app (Kotlin + Jetpack Compose), installable as an APK, with the desktop's
business rules, tested for parity with the desktop app.

- **Screens:** dashboard, customers, suppliers, bookings (passengers, flights, PNR), payments, expenses,
  refunds, invoices, reports, cashbook, backup/restore, settings.
- **Security:** passport numbers encrypted with an Android Keystore key, encrypted backups, device
  authentication, and no sensitive data in logs.
- **PDFs:** tickets, invoices, receipts and credit notes, made on the device.
- **CI:** builds a release APK, runs real tests (parity, money, backup/restore), and uploads the APK.
- **No cloud:** no cloud sync and no remote database.

## Architecture

- `android/engine`: **pure Kotlin/JVM**, holding all business logic. It is a line-by-line port of the iPhone engine
  `ios/AirZeloKit/Sources/AirZeloKit`, which itself passes desktop parity.
  - It runs on any SQLite through the `SqlDb` interface (`Db.kt`): `AndroidSqlDb` (the app) and `JdbcDb` (xerial
    sqlite-jdbc, engine tests only). A `SqlException` message is SQLite's own text (for triggers, the RAISE message),
    which `Agency.tx` turns into a validation error exactly as the iPhone does.
  - Money is `BigDecimal` with `HALF_UP` (Python `ROUND_HALF_UP`); amounts are integer paise in `Long`.
  - The schema is the desktop v4 schema in `engine/src/main/resources/com/airzelo/engine/schema.json`, generated by
    `python3 ios/tools/export_schema.py` (`--check` verifies the iOS and Android output).
- `android/app`: Compose app, `minSdk 30` (Android 11): the desktop's SQL uses upserts (`ON CONFLICT ... DO UPDATE`,
  SQLite 3.24+), and Android 11 is the first to ship SQLite 3.28. `settings.gradle.kts` includes `:app` unless
  `AZ_ENGINE_ONLY=1`, so the engine builds without an Android SDK.
- **Toolchain:** Gradle 8.10.2 (wrapper), Kotlin 2.0.21, AGP 8.7.3, JDK 17, compileSdk/targetSdk 35, Compose BOM
  2024.12.01, Robolectric 4.14.1.

### App (`android/app/src/main/kotlin/com/airzelo/app`)

- `AndroidSqlDb.kt`: one connection opened with `OpenParams` (WAL, `synchronous=FULL`, foreign keys); values bound
  with their real types through `SQLiteQuery` (not `rawQuery`'s text-only arguments); BEGIN/COMMIT/ROLLBACK mapped
  to Android's transaction API; row-returning PRAGMAs run as queries; snapshot = checkpoint + copy under a transaction.
- `DeviceKey.kt`: a random 32-byte master key, stored only wrapped (AES-256-GCM) by an Android Keystore key that never
  leaves the Keystore. The engine needs the raw master key because device backups derive their key from it with HKDF,
  exactly like the iPhone. Stored in `noBackupFilesDir`.
- `MainActivity.kt`: `FLAG_SECURE` (no screenshots, recordings or recent-apps preview); BiometricPrompt with
  `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`; locks on leaving the screen (not while the app itself opens the file picker
  or share sheet) and runs the automatic backup then. A phone with no screen lock opens with a plain warning.
- `AppModel.kt`: books, lock, revision counter; service refusals shown in a dialog, with **Save anyway** for the same
  warnings the desktop lets users override (duplicate PNR, possible duplicate payment ...). Error texts never include
  payloads.
- Screens: **Home** (dashboard: profit, cash, who owes whom, accounts, payment pending, departures, follow-ups),
  **Bookings** (search, detail, form with passengers + flights + PNR + prices + tax, status, refund / cancel,
  ticket PDFs, issue invoice), **Customers** (detail, balance, statement + CSV share, form with encrypted passport),
  **Money** (all entries, detail with allocations, reverse, receipt PDF, new entry incl. transfers), **More**:
  reports (13, CSV share), invoices & credit notes (PDF preview, cancel), suppliers, cash & bank accounts
  (cashbook per account), expenses, refunds & cancellations, backup & restore, company & documents settings,
  online features (unavailable, explained).
- Files: backup export and import through the system file picker (Storage Access Framework); PDFs and CSVs shared
  through a `FileProvider` from the app cache (old shared files deleted on each share); PDFs previewed with
  `PdfRenderer`.
- Manifest: **no INTERNET permission** (CI fails the build if one appears), `allowBackup=false` and data-extraction
  rules that exclude everything from Android cloud backup and device transfer.

### APK signing

- **Now:** no signing secrets exist, so every run signs with a **throwaway key made for that run** and names the file
  `AirZelo-<version>-android-THROWAWAY-KEY.apk`. It installs (allow "install unknown apps" for the browser/Files app),
  but a later build **cannot update it in place**: export a backup, uninstall, install the new APK, import the backup.
- **Permanent key (needs the owner's explicit approval first):** create a keystore, then add repository secrets
  `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. The workflow
  then signs with it and names the file `AirZelo-<version>-android-signed.apk`. Keep the keystore and passwords safe
  outside the repository: losing them means users must uninstall to update. Never commit a keystore (`*.jks` and
  `*.keystore` are git-ignored).

### How the key was set up (done; for reference or a new key)

1. Install a JDK for `keytool` (e.g. Temurin 17 from adoptium.net), then on the Mac, **outside the repository**:
   ```bash
   mkdir -p ~/AirZelo-signing && cd ~/AirZelo-signing
   keytool -genkeypair -v -keystore airzelo-release.jks -storetype PKCS12 -alias airzelo -keyalg RSA -keysize 4096 \
     -validity 10000 -dname "CN=ASHIQUE KALIPPADATH, O=AirZelo, C=IN"
   ```
   keytool asks for a password (use a long one; with PKCS12 the key password is the same).
2. **Back it up before anything else**: the file `airzelo-release.jks` and its password in a password manager, plus a
   second copy of the file on an encrypted USB drive kept offline. If the key is lost, no update can ever be
   installed over the app again (users would have to uninstall, after exporting a backup). Never email it, never put
   it in Git or a chat.
3. Add the secrets (each `gh secret set` asks for the value; nothing is stored in shell history):
   ```bash
   base64 -i ~/AirZelo-signing/airzelo-release.jks | gh secret set ANDROID_KEYSTORE_BASE64 --repo ashiquehanpgd-code/airzelo-travel-crm
   gh secret set ANDROID_KEYSTORE_PASSWORD --repo ashiquehanpgd-code/airzelo-travel-crm
   gh secret set ANDROID_KEY_PASSWORD --repo ashiquehanpgd-code/airzelo-travel-crm
   gh secret set ANDROID_KEY_ALIAS --body airzelo --repo ashiquehanpgd-code/airzelo-travel-crm
   ```
4. Publish (done for 0.3.0; next version: raise `versionCode`/`versionName`, then):
   ```bash
   git tag -a android-vX.Y.Z -m "AirZelo for Android X.Y.Z" && git push crm android-vX.Y.Z
   ```
   Then check Actions > android-release: it ends with "Public download verified: <url>".

Decide before the first public release (permanent afterwards): the Android application ID is `com.airzelo.app`
(the desktop's is `com.airzelo.crm`); the app name is `AirZelo` (as in `docs/RELEASE-IDENTITY.md`).

## Not done / known limits

1. **Not tried on a physical phone** (emulators only, without a real fingerprint sensor or screen lock). First on-device check: install, unlock (fingerprint and PIN), create a booking,
   PDF share to WhatsApp, export a backup to Files, import it, leave and return (lock + auto backup).
2. Android 11+ only (minSdk 30, see above). Supporting older phones would need a bundled SQLite (e.g.
   `androidx.sqlite:sqlite-bundled`) behind `SqlDb`.
3. Dates are typed as `YYYY-MM-DD` text fields (no date picker yet); the engine validates them.
4. Not ported from the desktop/iPhone: debt register screens, bank reconciliation screen (the engine has
   `reconciliationView` / `saveReconciliation`), tax-profile and currency editing screens, customer follow-up
   reminders as notifications.
5. Engine work runs on the main thread (one Agency, one thread, as on the iPhone). The 20,000-booking test loads in
   about 1 s on the CI JVM; a slow phone with very large books may feel a pause on backup/export (PBKDF2 600,000).
6. The iPhone `AgencyStore.listBackups()` has the bug fixed here for Android: it reads the kind with `split("-")`,
   so `pre-restore` backups show as "pre". Display only (pruning uses `auto`, which is unaffected).

## Conventions to keep

- Every service takes `Fields` (`Map<String, JValue>`) exactly like the desktop JSON API. Use `data.arg("key")` (not `data.get`).
- Never log payloads: they can contain passport numbers. The audit log stores passports only sealed or as "(encrypted)".
  The app has no `Log` calls; error dialogs show the service's message or SQLite's text, never bound values.
- A sealed value that can't be decrypted on this device is kept as is (`FieldCrypto.open` returns it unchanged).
- Re-saving a booking must start from `bookingEditFields(id)`, so no stored field or manual tax is lost (the booking
  form does this).
- `SqlDb` implementations put SQLite's own message in `SqlException.message` (optionally followed by `" in: " + sql`).
